# RCA — Échec extraction PDF en PRODUCTION (dossier-express, 2026-09-06 ~12:20–12:50 UTC)

## TL;DR — Verdict
Le correctif **est bien déployé** et **n'est pas** en cause. Ce n'est **ni** un problème de code obsolète (`pages[:30]`), **ni** une bascule Gemini intempestive. 

**Cause racine : crash-loop du pod backend provoqué par des ressources tier_0 insuffisantes.** La passe pdfplumber sur les 108 pages — bien que déportée via `asyncio.to_thread` — sature le CPU plafonné à **250m (¼ de cœur)** et, en tenant le GIL, affame l'event loop asyncio. Les sondes Kubernetes sur `/health` échouent (503 / EOF / connection refused) → K8s tue et redémarre le conteneur en boucle → la tâche d'extraction en arrière-plan (in-process) meurt à chaque redémarrage → le watchdog détecte « worker mort (heartbeat > 180s) » et relance depuis S3 → la passe lourde recommence → nouveau kill. La boucle ne converge jamais dans le budget de polling du frontend (4–6 min), qui abandonne et injecte le placeholder « [Extraction en cours — délai dépassé] ». L'analyse part alors sur un dossier vide.

Run actif au moment du test : **d014c967** (redeploy terminé 12:02:07 UTC) — et NON 57658dc7 (11:49:55). Un second redeploy a eu lieu à 11:54→12:02 ; le test 12:20–12:50 a donc tourné sur d014c967. Le fix est présent dans les deux, donc cela ne change pas le verdict.

## Réponses point par point

La seule trace applicative d'extraction est le watchdog :

- `12:37:03 INFO  - Extraction bdeb1116: reprise depuis S3 (1 fichier(s))`

→ L'extraction n'a **jamais terminé une seule passe** ; elle a été interrompue par la mort du pod avant de logger une méthode.

### 2. Durée réelle côté serveur / a-t-elle dépassé 4–6 min / abouti après abandon ?
Elle a dépassé le seuil `STALE_HEARTBEAT_S = 180s` (upload.py:156) → worker déclaré mort à 12:36:59, relancé depuis S3, **sans jamais aboutir** (aucun log de complétion d'extraction, ni avant ni après l'abandon du frontend). En pratique : boucle de redémarrage, pas une extraction lente unique.
NB : les deux lignes `[DOSSIER_EXPRESS][...][COMPLETE] path=native_anthropic` (12:07:17 chars=11739 ; 12:39:18 chars=13776) sont l'**analyse LLM** qui s'exécute sur le contenu placeholder/quasi-vide — ce ne sont PAS des complétions d'extraction.

### 3. Le build contient-il `for i, page in enumerate(pdf.pages):` (et PAS `pdf.pages[:30]`) ?
**CONFIRMÉ dans l'image déployée** (source du run d014c967 inspecté en sandbox lecture seule) :

- `PER_FILE_LIMIT = 800_000` présent (`backend/routes/dossier_express.py:87`).
→ Le correctif est intégralement présent. Le code n'est pas le problème ; c'est son coût CPU/mémoire face à tier_0.

### 4. Exceptions / OOM / kill / restart / timeouts dans la fenêtre ?
**OUI — pod backend en crash-loop pendant tout le test** (événements K8s du run d014c967, pod `...-mpgjj`) :
- `Started` count=4, `Created` count=4 → conteneur redémarré ~4 fois (derniers 12:37:56–57).
- Startup probe : `connection refused` ×18 (12:01→12:34:36) + `503` ×8 (jusqu'à 12:34:51).
- Liveness probe : `503` à 12:08:07 et 12:34:07 ; `EOF` à 12:05:38.
- `BackOff — Back-off restarting failed container` à 12:37:45.
- nginx (mêmes horaires) : `upstream timed out ... reading response header from upstream .../health` (event loop bloqué) puis `connect() failed (111: Connection refused) ... 127.0.0.1:8001/health` (process mort/redémarrant) à 12:01, 12:05–12:08, 12:34.
- `12:48:12 ERROR Campaign scheduler error: ...mongodb.net:27017: The read operation timed out` → corrobore la saturation de ressources.
Pas de raison `OOMKilled` explicite conservée (le pod crashé a été scale-down à 12:47:33, son `last_termination` n'est plus disponible), mais le motif 503→EOF→connection refused prouve sans ambiguïté des morts/redémarrages répétés du conteneur. Une contribution OOM (512Mi) reste probable (voir point 5).

### 5. Ressources / throttling CPU peut-il faire passer 16s → >4-6 min ?
**OUI — c'est le cœur de la cause.** Tier actuel = **tier_0 « Starter »** : CPU request 50m / **limit 250m**, mémoire request 200Mi / **limit 512Mi**, 2 replicas, pas d'autoscaling (hpa/vpa off).
- En préversion : CPU non plafonné → passe pdfplumber ~16,2s.
- En prod : plafond **250m = 0,25 cœur**. La passe s'allonge d'un facteur important, et surtout `pdfplumber.extract_text()` est CPU-bound Python qui **tient le GIL** : même via `asyncio.to_thread`, le thread partage le même plafond 250m et bloque l'event loop par à-coups → sondes `/health` en échec → **liveness kill**. `asyncio.to_thread` ne protège donc PAS contre le throttling CPU ni contre le GIL ici.
- Mémoire : 108 pages de texte + objets pdfplumber pour un PDF de 9,5 MB, dans 512Mi partagés avec le reste de FastAPI et une **2e extraction concurrente** (`2f9f65d7`, également pollée dans la même fenêtre) → risque d'OOM additionnel.

### 6. POST /api/upload/extract + GET extract-status : le mode async a-t-il démarré ? combien de polls ?
**Oui, le mode async a bien démarré.** Présence de `POST /api/upload/extract 200 OK` et de `POST /api/upload/chunk 200 OK`. Puis **des centaines** de `GET /api/upload/extract-status/bdeb1116... 200 OK` (répartis sur les 5 pods réseau .51/.52/.53/.54/.55) — cohérent avec un polling frontend jusqu'au timeout (120–180 tentatives × 2s). Un second dossier `2f9f65d7` est pollé en parallèle. Le pipeline async s'est donc lancé ; il n'a jamais abouti à cause du crash-loop.

## Chaîne causale complète
1. Upload OK → `POST /api/upload/extract` → `asyncio.create_task(_run_extraction(...))` (in-process, upload.py:401) démarre la passe pdfplumber sur 108 pages via `to_thread`.
2. tier_0 plafonne le CPU à 250m ; la passe CPU-bound tient le GIL → event loop affamé → `/health` renvoie 503 / timeout / EOF.
3. Kubernetes échoue les sondes liveness/startup → **tue et redémarre** le conteneur (± OOM sur 512Mi).
4. Le redémarrage détruit la tâche background in-process → heartbeat s'arrête → après 180s le watchdog du endpoint statut (upload.py:441) logue « worker mort » et **relance depuis S3** (upload.py:442) → la passe lourde recommence → re-kill. Boucle non convergente.
5. Frontend atteint son plafond de polling (4–6 min) → injecte « [Extraction en cours — délai dépassé] ».
6. `dossier_express` lance l'analyse LLM (`path=native_anthropic`) sur ce contenu placeholder → **dossier vide** (COMPLETE 12:07 & 12:39, chars ~12–14k = analyse du placeholder, pas du PDF).

## Ce qui est EXCLU
- Code obsolète (`pages[:30]`) : exclu — build vérifié, `enumerate(pdf.pages)` présent.
- Bascule Gemini malgré le fix : exclue — aucune trace Gemini/chunk.
- Bug applicatif d'extraction : le code fonctionne (16s en préversion) ; le problème est l'environnement d'exécution contraint.

## Recommandations (par ordre d'impact)
1. **Augmenter le tier** (Deployment Panel → Resources) : passer de tier_0 (250m CPU / 512Mi) à un tier ≥ tier_2/tier_3 pour disposer de plus de CPU (idéalement ≥ 1 cœur) et de mémoire. C'est le levier le plus direct et suffisant à court terme. (Décision utilisateur — coût crédits ; non effectué par moi, RCA en lecture seule.)
2. **Découpler l'extraction lourde du process web** (pour E1) : exécuter `_run_extraction` dans un worker/process séparé (ou `ProcessPoolExecutor`) plutôt qu'une `asyncio.create_task` in-process, afin que les sondes `/health` ne soient jamais impactées et qu'un kill ne détruise pas la tâche.
3. **Rendre la main à l'event loop pendant la passe** : chunker `_pdfplumber_pass_sync` (traiter par lots de N pages avec des `await asyncio.sleep(0)` / yields) pour éviter de bloquer le GIL en continu.
4. **Borner la concurrence** : sémaphore limitant à 1 extraction lourde simultanée par pod (2 extractions en parallèle observées ont aggravé la pression mémoire/CPU).

## Portée de la preuve
- Point 3 (contenu du build) : **vérifié en pod sandbox lecture seule** sur la source du run d014c967.
- Cause ressources/crash-loop : **diagnostiquée** à partir des logs prod, des événements K8s et de la config tier — non « reproduite » (le sandbox a un plancher de ressources supérieur et aucun secret, il ne peut pas rejouer le throttling/OOM prod).
